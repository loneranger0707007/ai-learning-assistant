5. Task 3: Domain and HTTPS (Reflective Implementation Plan)

Although a domain was not procured for this assignment, the following sequence details the precise steps I would execute to publish the service securely. Each action includes technical justification aligned with production best practices.

5.1 Domain Procurement

I would register the domain through Alibaba Cloud Wanwang to maintain account consolidation, simplify DNS zone management, and streamline billing. Given the academic scope, a cost-effective top-level domain such as .top or .xyz (approximately CNY 1–10 for the first year) satisfies the requirement without incurring premium pricing. I would configure a subdomain ai.example.top rather than apex domain usage, which avoids wildcard certificate complexity and isolates the AI service from potential corporate or personal root domains. Subdomains also facilitate future scaling (e.g., api.example.top, docs.example.top) under a unified DNS namespace.

5.2 DNS Configuration

Within the Alibaba Cloud DNS console, I would create an A record mapping ai.example.top to the ECS public IP 8.163.115.97. Setting the Time-To-Live (TTL) to 600 seconds balances propagation speed with cache efficiency, allowing rapid troubleshooting if misconfiguration occurs. Verification would proceed via terminal queries:

dig ai.example.top +short
nslookup ai.example.top

Both commands must return 8.163.115.97. Short TTLs are critical during initial deployment phases to minimize stale routing errors, and they are easily adjusted to higher values once stability is confirmed.

5.3 Security Group Adjustments

By default, the ECS security group permits only SSH and the application port. To support automated TLS provisioning, I would add an inbound rule allowing TCP ports 80 and 443 from 0.0.0.0/0. This is mandatory because Let's Encrypt's HTTP-01 challenge requires the ACME server to initiate an unauthenticated HTTP request from arbitrary IP addresses to validate domain ownership. Without open ports 80/443, certificate issuance fails silently. Once HTTPS is operational, the public rule for port 14242 would be removed, ensuring all external traffic must traverse the reverse proxy.

5.4 Nginx Reverse Proxy Configuration

Nginx serves as the edge router, terminating external connections and forwarding requests internally. Installation follows standard package management:

sudo apt update && sudo apt install nginx -y

The server block at /etc/nginx/sites-available/ai-learning would contain:

server {
    listen 80;
    server_name ai.example.top;

    location / {
        proxy_pass http://127.0.0.1:14242;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        
        # Critical for AI artifact generation (20-60s)
        proxy_read_timeout 360s;
        proxy_send_timeout 360s;
    }
}

Enabling the site involves symlinking to sites-enabled/, validating syntax with nginx -t, and reloading with systemctl reload nginx. The extended timeouts are non-negotiable: the default 60-second limit triggers 504 Gateway Timeout errors during complex prompt processing or image generation. Header forwarding ensures the FastAPI application receives accurate client metadata for logging, rate limiting, and CORS enforcement.

5.5 HTTPS Provisioning with Certbot

Certbot automates Let's Encrypt integration, eliminating manual CSR generation and expiration tracking:

sudo apt install certbot python3-certbot-nginx -y
sudo certbot --nginx -d ai.example.top

The wizard interactively selects the server block, enforces HTTP-to-HTTPS redirection, and configures systemd timers for automatic renewal every 90 days. This approach guarantees cryptographic freshness without administrative overhead, aligning with modern zero-trust transport requirements.

5.6 Access Control Layer

To satisfy academic privacy expectations, I would implement HTTP Basic Authentication at the Nginx level, creating a distinct security boundary from the application's BNBU login mechanism:

sudo htpasswd -c /etc/nginx/.htpasswd admin
sudo chown www-data:www-data /etc/nginx/.htpasswd

Adding auth_basic "Restricted AI Assistant"; auth_basic_user_file /etc/nginx/.htpasswd; inside the location block introduces a second authentication gate. The resulting three-layer model comprises: (1) TLS encryption for confidentiality, (2) Nginx Basic Auth for network-level authorization, and (3) BNBU OAuth/login for application-specific permissions. This separation prevents credential collision and allows independent rotation policies.

5.7 Final Hardening

Post-deployment verification includes removing the 14242 public ingress rule from the security group, restricting SSH access to my static IP, and confirming health via curl -I https://ai.example.top. Successful responses should return 200 OK with Strict-Transport-Security headers, indicating active HSTS enforcement and proper proxy chaining.

6. Security Analysis

The deployment employs defence-in-depth by stacking complementary controls rather than relying on a single perimeter. Transport Layer Security (TLS) ensures data integrity and confidentiality in transit, mitigating man-in-the-middle attacks on campus or public networks. The security group enforces network-level least privilege, exposing only necessary ports to the internet. Application secrets reside exclusively in model-secrets.env, which is gitignored and injected at container runtime, preventing accidental commits to version control. The container itself runs with minimal capabilities, avoiding host-level privileges.

However, HTTP Basic Authentication presents inherent limitations. Credentials are transmitted as base64-encoded strings, which are trivially decoded without encryption. Its security posture depends entirely on TLS wrapping the channel; without HTTPS, passwords travel in plaintext. For production environments, this pattern is insufficient. An OpenID Connect (OIDC) provider or identity-aware proxy (e.g., Alibaba Cloud RAM, Keycloak, or Traefik ForwardAuth) would replace Basic Auth with token-based, scoped, and revocable credentials. Additionally, implementing rate limiting, WAF rules, and regular dependency scanning would further reduce attack surface. The current design prioritizes educational clarity and rapid iteration, acknowledging that academic deployments trade some enterprise rigor for pedagogical transparency.

8. Reflection and Improvements

The transition from local Docker to cloud ECS proceeded smoothly, validating the reproducibility of containerized workflows. ACR eliminated environment drift, and ECS provided predictable compute performance. However, several architectural decisions warrant revision upon future iterations.

First, provisioning the ECS instance in the Hong Kong region from the outset would circumvent ICP filing ambiguities and latency penalties associated with mainland Chinese regions. Academic projects rarely require mainland compliance, and HK deployment accelerates time-to-market while maintaining low-latency access for BNBU students. Second, binding the container port to 127.0.0.1:14242 instead of 0.0.0.0:14242 would enforce localhost-only connectivity, forcing all external traffic through Nginx and preventing direct container exploitation. Third, automating Nginx configuration, Certbot execution, and security group updates via a Bash script or Infrastructure-as-Code tool (Terraform/Ansible) would reduce human error and enable one-click environment recreation.

Finally, replacing HTTP Basic Authentication with an OIDC-compliant identity provider would align the deployment with modern zero-trust architectures. Token-based sessions support MFA, conditional access, and centralized audit logging, addressing the fundamental weakness of base64-encoded credentials. Integrating monitoring via Prometheus/Grafana and log aggregation via ELK would further enhance observability. These improvements transform a functional academic prototype into a resilient, production-ready cloud service, fulfilling the course objective of bridging AI agent development with enterprise-grade deployment practices.
